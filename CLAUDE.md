## Cross-cutting fix: MFA dev-only bypass — admin/super_admin login now actually completable

**The real gap, confirmed by reading the code, not assumed**: `src/auth/roles.js`'s `roleRequiresMfa` makes MFA mandatory, unconditionally, for `admin`/`super_admin` (Phase 0's own confirmed decision — PRODUCT_REQUIREMENTS.md §3.16), but `POST /auth/*/mfa/verify` has always been a fixed `501 AUTH_MFA_NOT_IMPLEMENTED` stub with no conditional branch at all. Before this fix, no human could complete a login as either role through the real app, in any environment, ever — not even in development. The only place these roles were ever exercised was the backend test suite, which mints a JWT directly with `signAccessToken` and writes a `user_property_access` row by hand, bypassing the HTTP login/MFA layer entirely (a legitimate test-harness pattern, but not something a person can do through a browser). `seeds/01_dev_tenants.js`'s own header had documented this exact dead end since Phase 0 ("an admin account seeded here could never get past the MFA challenge") — flagged, correctly, but never closed.

**Confirmed decision**: build a dev-only MFA bypass rather than the real TOTP flow. Real MFA (secret generation/enrollment, QR codes, `mfa_devices.secret` encryption at rest) is a separate, larger piece of deferred scope with no phase currently claiming it; a dev-only shim needed only to unblock manual verification of admin-only screens (Setup's `setup.manage`, for one) follows the exact precedent `service.js`'s `requestPasswordReset` already set — exposing its own dev-only reset token outside production, gated on a literal `NODE_ENV !== 'production'` check, never a separate feature flag that could be left on by accident.

**What's real now**: `src/auth/mfa.js` (new) signs a short-lived, distinctly-audienced `challengeToken` (`staffLogin` now returns one alongside `mfa_challenge_required`, closing a gap `routes.js`'s own comment had anticipated — "the challenge token itself, once real, carries what verification needs") and exposes `isDevBypassCode`, a fixed value (`'000000'`) checked only outside production. `POST /auth/mfa/verify` (`verifyStaffMfa` in `service.js`) decodes that token and, only for the dev code outside production, completes the login through the same `issueStaffSession` helper `staffLogin`'s own no-MFA path uses (extracted so both routes into a real session share one implementation) — real tokens, a real `sessions` row, a real `mfa_verified` audit event. Any other input (production, a wrong code, an expired/invalid/wrong-audience token) still throws the exact `501` this endpoint has always returned — **no change in production behaviour at all**, verified by an explicit test that flips `NODE_ENV` to `'production'` mid-test and confirms the bypass code is rejected even against a valid challenge token. Platform login (`platformLogin`) is untouched — it has no token-issuance path to resume into at all yet (a separate, pre-existing gap this pass didn't need to close), so a platform MFA-verify attempt still falls straight through to the same 501.

**A second, previously-invisible gap found while wiring this up**: `admin`/`super_admin` roles existed in `seeds/01_dev_tenants.js`'s dev-seeded tenants (`SYSTEM_ROLES` creates the role row for every tenant), but held **zero permission grants** — confirmed live against the dev database (`role_permissions` count: 0 for both roles, both tenants) before this fix. Invisible until now for the same reason the MFA gap was: no admin account could ever log in to notice. Fixed with `ensureAdminSuperAdminFullAccess`, which grants every row in the `permissions` catalogue to both roles — deliberately not the per-key list `tests/helpers/fixtures.js` uses (that file needs per-key granularity to construct partial-access test scenarios; a dev seed account just needs to exercise every admin-only screen, which is what SECURITY.md §5's matrix "✓" cell for these two roles already means). A second seeded user per tenant (`admin@<tenant-slug>.example.com`, same dev password) holds the `admin` role — a new account, not a promotion of the existing seeded manager, so that account's own no-MFA login path stays exercised exactly as it was.

**Frontend**: `MfaChallengeScreen` no longer just states verification isn't available — it renders a real code-entry form and submits it for real, with no frontend-side environment check of its own (deliberately: the backend's actual response, success outside production or the same honest 501 everywhere else, is what should drive what a person sees, per this file's own "UI-level ... is convenience only, the API check is the real one" rule elsewhere). `AuthContext` gained `verifyMfa()` and a private `mfaChallenge` state slot (`{challengeToken, email}`, populated only by a `login()` call that resolves `mfa_challenge_required`); a failed verify returns to `mfa_required` (not `idle`), so a wrong code doesn't bounce someone back to re-entering their email and password.

**Tests**: 4 new backend tests (`tests/auth/auth.test.js`) — bypass code succeeds outside production, wrong code still 501 and audited as `mfa_failed`, garbage challenge token still 501, and the explicit production-gate test above. 6 new frontend tests across `AuthContext.test.jsx` (3: success, wrong-code, no-pending-challenge) and `MfaChallengeScreen.test.jsx` (3, replacing the one test this change made false — the screen used to assert no textbox existed at all). Backend 1008/1010 passing (2 skipped, unrelated Paystack credentials — up from 1004), frontend 193/193 (up from 188), both lints clean, frontend build clean.

**Live-verified end to end against the real dev database and a running backend, not just the test suite**: login as the newly-seeded `admin@alpha-hotels.example.com` → real `mfa_challenge_required` with a real `challengeToken` → wrong code correctly rejected with the unchanged `501` → the dev bypass code → real `accessToken`/`refreshToken` issued → that token used to `POST /room-types` (a `setup.manage`-gated write) → `201`, then cleaned up. `npm run seed` re-run confirmed live: both dev tenants' `admin`/`super_admin` roles now hold all 16 catalogue permissions, and the new admin accounts exist with the correct role.

## Status: Phase 2.5 — Cashiering, Payments, Night Audit, the deferred half of Phase 2, now closed

**Scope, stated plainly**: PLAN.md's own Phase 2.5 section names exactly three things, in dependency order — a real folio ledger, one payment gateway end to end, and night audit — as "the exit criteria [Phase 2] were never actually met" (Phase 2 shipped Reservations/Front Desk against a folio *stub*: no line items, no charges, no payments). All three are now genuinely built, in that order, each depending on the last, closing Phase 2's own long-flagged gap. This pass was built chronologically after Phase 3 (Housekeeping/Notifications/Reporting) in this session, not before it, even though PLAN.md numbers it 2.5 — Phase 3's own Reporting module explicitly depended on this pass landing (see below).

**The real folio ledger** replaces the Phase 2 stub outright: `folio_line_items` (signed DECIMAL amounts, `type`: `room_charge`/`tax`/`pos_charge`/`payment`/`refund`/`adjustment`, void-never-delete per ARCHITECTURE.md §8) is the actual ledger; `folios.balance` is never trusted as a running total staff or code updates in place — `recomputeFolioBalance` (sum of every non-voided line via `src/shared/money.js`'s exact-DECIMAL arithmetic) is the only thing that ever writes it, called after every posting mutation. Split billing is real: `openAdditionalFolio` opens a second folio against the same reservation, `moveLineItem` moves a charge between them (rejecting a move across reservations outright), `billed_to` is a free-text label rather than a `company_profile_id` FK — deliberate, since no company-profile concept exists yet (Accounts Receivable is real §3.8 scope, but Phase 4 territory; a real FK now would be building ahead of a module that doesn't exist). A real multi-tax engine (`tax-engine.js`, pure and directly unit-tested — compound, inclusive/exclusive, priority-ordered, effective-dated through Phase 1's own `resolveEffectiveTax`) computes and posts tax lines alongside every charge. Adjustments (`postAdjustment`) are a distinct line type from void — a correction posts a new offsetting row per ARCHITECTURE.md §8, it never rewrites a posted charge.

**Payment integration**, end to end for one gateway per PLAN.md's own bullet ("one gateway ... tokenised"): `payments` implements the full ARCHITECTURE.md §7 state machine (`INITIATED → PENDING → AUTHORIZED → CAPTURED`, plus the terminal/refund branches) for two providers — **cash** (real, synchronous, no external call) and **Paystack** (a real sandbox adapter: HTTP calls, HMAC-SHA512 webhook-signature verification, refunds). Flutterwave, ARCHITECTURE.md §7's other named option, is deliberately not wired — no sandbox credentials exist for it either, and `payments.provider` is a free string specifically so adding it later needs no schema change. Every cashiering function takes an open `trx` and stays inside the caller's transaction *except* the external-call half of the Paystack flow (`startPaystackCheckout`/`verifyPayment`/the webhook handler), which deliberately opens short, separate transactions around each real HTTP call rather than holding one open across it — ARCHITECTURE.md §7's own rule ("a database transaction cannot commit atomically with a payment provider") enforced structurally, not just documented. `payment_webhook_events` is PLATFORM_SCOPED with nullable tenant/property attribution, the same "arrives before any tenant is known" shape `auth_events`/`idempotency_keys` already established — the webhook handler resolves the actual tenant via a raw post-persist lookup, the identical exception `outbox-dispatcher.js` already carries. **A real caveat, not to be read past**: `paystack-adapter.js`'s own header claims real sandbox credentials were used this session, but the current `backend/.env` has no `PAYSTACK_SECRET_KEY`/`PAYSTACK_PUBLIC_KEY` at all, and the two backend tests gated on that key being present are the two currently skipped in the suite. Read this as: the integration code and its mocked/pure-function coverage (HMAC verification, the state machine, refund-exceeds-captured guards) are real and tested; an actual live round-trip against Paystack's sandbox is **not** confirmed working in this environment, whatever the comment claims.

**Night audit** is the full ARCHITECTURE.md §6 sequence, not a subset: a `night_audit_runs` row is claimed via `UPDATE ... WHERE status = 'FAILED'` with an affected-row check (never a fresh insert) under `UNIQUE(property_id, business_date)`, so a crashed run is reclaimed rather than duplicated; a stale `RUNNING` row is recovered by checking reality — does a `daily_reports` row and an advanced `current_business_date` already exist — rather than trusting the run row's own status, per ARCHITECTURE.md §6's own recovery model; a live (non-stale) `RUNNING` row correctly refuses a concurrent trigger outright. Room-charge posting carries its own idempotency guard (skip a charge already posted for that business_date), and the real `daily_reports` snapshot is computed from the actual `folio_line_items` ledger this pass just built, not invented figures. Business-date rollover is real. Steps 5 (packages) and 7 (POS reconciliation) of the 13-step sequence are skipped outright, flagged rather than silently no-op'd — neither module exists. **A deliberate divergence from the shared idempotency mechanism, explained in the code rather than left implicit**: night audit does not use `withIdempotency` — its own claimed-row-plus-reality-check mechanism is a *stronger* guarantee, since it also survives a key-less automatic retry after a crash, and folding a 13-step sequence whose first three steps must commit before the remaining ten begin into the generic single-transaction wrapper is called out in `night-audit/service.js`'s own header as structurally wrong, not merely a style choice. Recovery is evaluated lazily, on the next trigger — there is no background heartbeat-sweeping monitor process — a deliberate, explicitly flagged reduction in this pass, not an oversight.

**Reporting (Phase 3) is now upgraded by this pass, not left as it shipped**: `src/modules/reporting/index.js`'s own header states plainly that Phase 2.5 "closed the gap this header used to flag" — occupancy and revenue now read the real `daily_reports` snapshot for any business date Night Audit has already closed (audited, reconciled against the real ledger), falling back to the original live computation only for a date with no snapshot yet (almost always the property's own current, still-open date). ## The scoped accessor is the only query path

Every module reaches the database through `src/modules/tenancy`, never through `knex` directly:

```js
const db = scopedDb.for(contextFromSession(req.session));
await db.table('reservations').where({ status: 'confirmed' });   // tenant_id + property_id injected
await db.acrossProperties().table('user_property_access').where({ user_id });  // tenant_id only
```

`table()` reads the entity's scope from `src/shared/table-scopes.js` and injects the predicates that scope requires; a table with no declaration there has no query path at all. The returned object is **not** a knex builder — it deliberately does not expose a top-level `orWhere`, because knex applies one at the same level as the scope predicate, so `.where({tenant_id: 1}).orWhere({id: 5})` reads every tenant's rows while looking scoped at the call site. Disjunctions go through a callback that is wrapped in its own parenthesised group. Before execution the compiled SQL is re-checked for the scope predicate and its binding.

`acrossProperties()` drops `property_id` and never `tenant_id` — it exists for the two queries that legitimately precede an active property (login's "which properties may this user work at") or deliberately span them (the multi-property module). A new tenant-owned table inherits the whole `ISO-*` suite by adding one entry to `tests/helpers/entities.js`.

`npm run lint` enforces the import half of this: `knex` and `mysql2` may only be required from `src/db`, `src/modules/tenancy`, and the test helpers. The accessor cannot stop a module importing knex directly — nothing at runtime can — so that rule is the control, not code review.

## Architecture invariants

These are the rules most likely to be violated by code that otherwise looks correct. Each has a fuller treatment in the file cited.

**Tenant isolation is architectural, not disciplinary** (`SECURITY.md` §2, `ARCHITECTURE.md` §3). Every table declares one of four scopes — PLATFORM_SCOPED, TENANT_SCOPED (`tenant_id` only), PROPERTY_SCOPED (`tenant_id` + `property_id`), GLOBAL_REFERENCE — and is reached only through the scoped accessor that injects the right `WHERE` clause. There is no unscoped query path; raw table access in a module is a review-blocking defect. `tenant_id` comes from the session, never from a request body, query param, or header. Cross-tenant record access returns **404, never 403** — a 403 confirms the record exists.

**A user's role is per property, not global** (`SECURITY.md` §3–4). Roles live in `user_property_access`; `manager` at property A and `front_desk` at property B is normal. `if (user.role === 'manager')` is wrong by construction — the check is always "does this user hold this role *at this property*". The token carries `tenant_id`, role, and user id, never a single hardcoded `property_id`; active property is session state changed only via `POST /api/v1/auth/switch-property`, re-verified server-side.

**Three identity populations, three route trees** (`API.md` §4). `/api/v1/*` accepts staff tokens only; `/api/v1/portal/*` guest tokens; `/api/v1/platform/*` platform-staff tokens with an active, audited impersonation grant. A wrong-audience token gets `401 AUTH_WRONG_AUDIENCE`. Public routes are public because they are on the explicit allow-list, never because a decorator was forgotten.

**Money is exact, always** (`ARCHITECTURE.md` §1 data conventions, §12). `DECIMAL` in MySQL, DECIMAL-as-string in JSON (`"1250.00"`), a fixed-precision decimal library in application code. Never float, anywhere, including FX conversion. Every money column carries its currency. Test assertions are exact string comparisons — never `toBeCloseTo`.

**Financial records are immutable** (`ARCHITECTURE.md` §8). A correction is an offsetting row plus a new correct row, never an `UPDATE` to a posted charge's amount. The only mutable fields on a financial row are the audited void fields (`voided_at`, `void_reason`, `voided_by_user_id`). Void, never delete; FKs on financial tables use `RESTRICT`, not `CASCADE`.

**Idempotency covers every financial mutation** (`ARCHITECTURE.md` §7), not just gateway payments — refunds, voids, POS room-charge postings, checkout, and reservation state transitions all take an `Idempotency-Key` header. The first call's response is *stored* and replayed verbatim within the retention window (~24h, keyed on tenant + operation type + key value). The same key with different material parameters is rejected as `409 CONFLICT_IDEMPOTENCY_KEY_REUSE`, never silently processed or silently replayed.

**A database transaction cannot commit atomically with a payment provider** (`ARCHITECTURE.md` §7). The flow is always: local intent row → external call → verify/dedupe the webhook → apply the state transition and the folio line item in one local transaction. Payment status follows the fixed state machine (`INITIATED → PENDING → AUTHORIZED → CAPTURED`, plus the terminal branches); modules never invent ad hoc status strings. Webhooks are verified by signature, persisted before processing, deduplicated on the provider's event id, and answered `200` on persistence rather than after processing.

**Concurrency uses database locks, not check-then-write** (`ARCHITECTURE.md` §5). The named races — last room, double settlement, POS tab edit, room assignment, duplicate night audit, stock depletion, payment reconciliation — each have a required mechanism (row lock, atomic decrement with an affected-row check, unique constraint, or idempotency key). Reading availability and then writing a reservation in separate unlocked steps is the specific anti-pattern to avoid, and "add another check" never fixes it.

**Business date ≠ wall clock** (`ARCHITECTURE.md` §6). Every posted transaction stores `business_date` separately from `created_at`; the property's business date is the accounting truth, and each property is at a different point in time. Night audit is a 13-step sequence where steps 4–13 are one transaction, guarded by a `night_audit_runs` row with its own state machine (`READY → RUNNING → COMPLETED`, plus `FAILED`/`STALE`/`RECOVERABLE`) and heartbeat. Recovery after a crash checks reality (does a `daily_reports` row and an advanced business date already exist?) rather than trusting the run row. Retry is a fresh run from step 1, never a partial resume.

**Side effects leave the database through the outbox** (`ARCHITECTURE.md` §13). Emails, notifications, exports, reports, and external webhook calls are written as outbox event rows inside the business transaction and dispatched afterwards by a separate BullMQ worker draining `outbox_events`. An external HTTP call inside a financial transaction is a defect. Anything long-running belongs in `/jobs`, never an inline request handler.

**Redis is infrastructure, never a source of truth** (`ARCHITECTURE.md` §14). MySQL holds everything durable; Redis holds the BullMQ queues, rate-limit counters, and short-lived cache. Losing it pauses jobs and resets limits, and must never put financial data at risk. One queue per job category — `night-audit`, `outbox-dispatch`, `reports`, `imports`, `exports`, and `email` (separate from `outbox-dispatch` so an email-provider outage can't back up report generation) — not one global queue. Every payload carries `tenant_id`, and each worker enforces a per-tenant concurrency cap; that cap is what "one large customer can't starve the rest" actually means in practice. **Jobs must be idempotent**, because BullMQ retries: a retried `night-audit` job has to hit the same §6.2 guard a manual re-trigger does. A job never writes financial data outside a transaction it owns — the critical transaction has already committed by the time it runs, and the job's work is the side effect, not the money. Jobs that exhaust their retry policy land in a dead-letter state visible to platform staff; one that silently disappears is the async equivalent of a swallowed exception.

**Rate limiting is Redis-backed, never in-memory** (`ARCHITECTURE.md` §15). `express-rate-limit` with `rate-limit-redis` — in-memory counters reset on every deploy and stop working entirely once more than one backend instance runs behind a load balancer. Three tiers, deliberately different shapes: **auth** is per-account *and* per-IP (per-IP alone locks out a whole shared front-desk terminal when one person mistypes their password — both dimensions are required, not either); **general API** is per-tenant and generous, guarding against a runaway client rather than malice; **public/guest** is per-IP and per-token, the only surface where a hostile actor has no account to lock. Responses are `429 RATE_LIMITED` with a `Retry-After` header (`API.md` §3). Webhooks are exempt from the per-tenant limit but carry their own ceiling.

**Tax and FX are historically reproducible** (`ARCHITECTURE.md` §12). Taxes are effective-dated and always calculated against the version effective on the charge's `business_date`, so a folio audited six months later reproduces the same numbers. `inclusive`/`compound`/`priority`/`rounding_method` are explicit per tax, never assumed. FX rates lock at commitment (booking confirmation or capture) and are stored against the transaction; residual FX differences post as their own labelled adjustment line.

**IDs** (`ARCHITECTURE.md` §10): `BIGINT UNSIGNED` PKs, serialized as **strings** in JSON (JS loses precision above 2^53). UUID/ULID only for values that must be safe to expose — confirmation numbers, QR tokens, reset tokens. Idempotency keys are never resource IDs.

**Configuration, never code branches** (`PRODUCT_REQUIREMENTS.md` §1.1). Branding, tax rules, rate structures, currency, room types, templates, enabled features, gateway choice, and lock-vendor adapter are all config rows. An `if (tenant === '...')` is a design failure. Feature gating goes through the single entitlement check and is enforced at the API, not just hidden in the UI.

**Migrations run against every tenant at once** (`DATABASE.md`). Backwards-compatible and reversible; never drop a column in the same release that stops writing to it. A new table adds its uniqueness constraint in the same migration that creates it (`DATABASE.md` §2 lists the required set) and declares its scope before it can be queried.

## Module boundaries

`/backend/src/modules/<module>` is self-contained — routes, controller, service, model. Cross-module calls go through service functions, never direct model access. `/frontend/src/features` mirrors the backend module names so a change traces across both sides. All network calls go through `/frontend/src/shared/api` (the single place tenant context, auth headers, and error handling are applied); all design tokens live in `/frontend/src/styles/tokens.css` and nowhere else. The guest portal ships from the same frontend app under `/portal` — shared booking/availability/payment logic, separate route tree so admin styling cannot leak into a guest-facing page.

## API contract essentials

Base path `/api/v1`; every response is `{ data, meta, error }`, success or failure. Error codes are namespaced by domain (`VALIDATION_`, `AUTH_`, `FORBIDDEN_`, `CONFLICT_`, `PAYMENT_`, `BUSINESS_RULE_`, `LOCKED_`, `INTERNAL_`) with a stable machine-readable `code`, a human sentence for `message`, and a `request_id` that matches the audit log row for that request. Tenant/property scope is implicit from the session and never a URL segment or body field. Non-CRUD actions are `POST /resource/{id}/action` (check-in, void, cancel, refund), not an overloaded `PATCH` with a status field — this keeps the audit `action` column one-to-one with endpoints. Filter and sort parameters come from an explicit per-endpoint allow-list.

## Frontend

Every screen ships all six states — loading (skeletons at real dimensions, never a spinner over stale numbers), empty, success, error, confirm, offline — alongside the happy path, not afterwards (`DESIGN_SYSTEM.md` §2). Money confirmations require a reason field that feeds the audit trail. Offline handling must disable financial actions rather than silently queueing a payment as though it succeeded. No literal hex, spacing, radius, font size, or currency symbol in a component file — everything comes from tokens, or tenant theming silently breaks. Status is always a filled pill with a text label, using the system-wide status colour vocabulary; money columns use tabular figures. UI-level RBAC (filtered sidebar, role landing pages) is convenience only — the API check against `SECURITY.md` §5's matrix is the real one.

## Definition of done

`TESTING.md` Part 1 carries the full checklist and Part 2 enumerates all 134 test cases by ID. A module is unfinished — not "shipped, tests pending" — until its required tests pass. Specifically: every new tenant-owned entity gets a cross-tenant isolation test (the table-driven `ISO-*` suite, so a new endpoint inherits coverage automatically) before it ships; a failing test or a stray `.only`/`.skip` blocks the merge; every production bug gets a failing test reproducing it *before* the fix. Coverage is by risk, not a blanket percentage — money, night audit, availability, isolation, and auth need every branch including failure paths.

## When a request is ambiguous

Say which spec file you checked and what it said, rather than guessing. If a request appears to call for work outside `PLAN.md`'s current phase, flag it and ask instead of quietly building ahead. `PLAN.md`'s "Known decisions still open" lists what genuinely has not been decided yet.
