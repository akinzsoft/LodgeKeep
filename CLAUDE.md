## Status: Phase 2 — Reservations & Front Desk, partially built (not PLAN.md's full exit criterion)

**Scope, stated plainly**: PLAN.md's Phase 2 bullet list is "the core operational loop" — Reservations, Front Desk, Rooms, Cashiering, Guest Profiles, Night Audit, and one payment gateway end to end, with an exit line of "book, check in, post charges, take payment, check out, close the day, roll the date." This pass built exactly two of those bullets — Reservations (§3.2) and Front Desk (§3.3) — the user's own explicit scoping, confirmed before any design work started. **Cashiering, Guest Profiles (as a real module), Night Audit, and payment integration were not built.** PLAN.md's own Phase 2 exit line therefore cannot be true from this pass alone — it structurally needs Cashiering (folios with real line items) and Night Audit (business-date rollover, charge posting) too. Don't read this section as claiming the full loop works; it doesn't yet.

**Four real dependencies didn't exist, and three were deliberately built as minimal stubs rather than expanded scope**: Reservations cannot function without a guest to book for, a room-type-level sellable-inventory count to check against, and — per ARCHITECTURE.md §11's own state machine — a folio to open at check-in. None of `guests`, `room_type_inventory`, or `folios` existed after Phase 1. Each was confirmed with the user as a minimal stub rather than pulling a whole future module forward:
- **`guests`** — TENANT_SCOPED (confirmed two ways, not guessed: `guest_accounts.guest_id`'s own Phase-0 comment already said "the tenant-level `guests` row ... FK added with the guests table in Phase 2," and DATABASE.md's own `reservations` row says the same). Just `first_name`/`last_name`/`email`/`phone` — no search, no stay history, no loyalty fields. A real Guest Profiles pass (§3.1) extends this table; it does not replace it. The FK from `guest_accounts.guest_id` was wired in the same migration that creates `guests`, closing a forward-reference left open since Phase 0.
- **`folios`** — a bare stub (`reservation_id`, `status`, `balance`, `currency`) opened at check-in, closed at check-out. No `folio_line_items`, no payments, no split billing. `balance` starts at `0.00` and the only thing in this whole pass that ever changes it is an early/late checkout fee (below) — check-out's "folio balance must be zero" precondition is real code, just checked against a balance nothing else can move yet.
- **`room_type_inventory`** — DATABASE.md files this under the Setup module (§3.19), but Phase 1 never built it and Reservations cannot compute sellable inventory or run the last-room race without it, so it landed here instead as a Reservations prerequisite. **Its physical-availability column does not exist as designed in the original DATABASE.md row** — that row named a stored `physical_rooms` column; this pass computes physical availability *live* at lock time as `COUNT(rooms WHERE room_type_id = X AND status = 'active')` instead, and DATABASE.md's own row for this table has been rewritten to match (see that file directly, and the migration's own header, for the full reasoning: a cached count needs every room create/archive/out-of-service transition to also write here for every already-generated future date, which is a second source of truth that drifts). The real, flagged cost: a room's *current* status is reflected everywhere instantly, but there's no way yet to schedule a *future* out-of-service window — that needs date-ranged `out_of_order_periods` (Rooms/Housekeeping, §3.6), not built.
- **Idempotency itself** — ARCHITECTURE.md §7 and §11 require an `Idempotency-Key` on every financial mutation and every reservation transition, and no mechanism for this existed anywhere in the codebase. `src/shared/idempotency.js`'s `withIdempotency()` is that mechanism now, backed by a new `idempotency_keys` table (TENANT_SCOPED, ARCHITECTURE.md §7's own scoping) — built as shared infra from the start, not a reservations-module one-off, since Cashiering and Night Audit will need the identical mechanism. It opens exactly one transaction per request and hands the transaction-bound accessor down to the caller's handler, so the idempotency-key bookkeeping row commits atomically with the mutation it's bookkeeping — never one without the other.

**Three confirmed design decisions that shape the schema**: (1) a specific physical room is assigned only at check-in, never at booking — booking reserves a room *type* and a date range, `reservation_rooms` gets its first row at check-in, and `reservations` itself deliberately carries no `room_id` column. (2) `WAITLISTED` is a real, distinct value in the reservation status enum, not aliased onto `TENTATIVE` — ARCHITECTURE.md §11's own state-machine table doesn't enumerate it (this schema's extension), but PRODUCT_REQUIREMENTS.md §3.2 gives waitlist its own UI screen and its own status-filter language, which aliasing would have contradicted. A waitlisted reservation holds no inventory; `promoteWaitlist` is what actually acquires it, and can fail (staying waitlisted) exactly like a fresh booking can. (3) `market_segment_id`/`booking_source_id`/`cancellation_policy_id`/`group_block_id` are present as nullable, FK-less columns on `reservations` — named now so a later migration adding one of those parent tables only needs to add the constraint, not the column, the same forward-reference pattern `guest_accounts.guest_id` itself used from Phase 0 until this pass filled it in.

**The concurrency requirement, proven for real, not just asserted**: PLAN.md names the last-room race as this phase's one thing to "pull forward deliberately." `reserveInventoryForDates` (`src/modules/reservations/service.js`) does insert-if-missing then `SELECT ... FOR UPDATE` then check-and-increment, once per night of the stay, all inside one transaction — a failure on any single night aborts the whole reservation, never a partial hold. **Proving this needed a second, structurally different test file.** Every other test in this codebase shares one rolled-back transaction per file (`useTestApp()`); two "concurrent" requests against that harness are really two savepoints on the *same* MySQL session, and a session never blocks its own lock — `tests/isolation/scoped-accessor.test.js`'s own existing comment on this exact limitation says so explicitly, and stops short of a live two-writer test for the same reason. `tests/reservations/concurrency.test.js` is the real version: it binds the app to the actual pooled test connection (`knexfile.js`'s `test.pool: { min: 1, max: 5 }`, sized with a comment already anticipating exactly this need), seeds real *committed* rows (cleaned up in `afterAll`, since nothing here is inside a transaction to roll back), and fires two genuinely concurrent HTTP requests — confirmed live to produce exactly one `201` and one `422 BUSINESS_RULE_OVERBOOKING_THRESHOLD_EXCEEDED`, with `rooms_sold` landing at exactly `1`, never `0` or `2`.

**RBAC: manager gets full access here, deliberately unlike Setup's read-only grant.** Four new permission keys — `reservations.view`/`.manage`, `front_desk.view`/`.manage` — split across two SECURITY.md §5 matrix rows in one backend module (`src/modules/reservations`; see that module's own `routes.js` header for why one module serves two permission domains rather than two modules). `front_desk`/`manager`/`admin`/`super_admin` roles get all four; `cashier` gets `reservations.view` only, nothing on Front Desk — the matrix's own real distinction, not a simplification. Manager's *full* grant here (as opposed to Setup's view-only) isn't an inconsistency — it's what SECURITY.md §5's matrix actually says for these two domains, carried through faithfully into both `tests/helpers/fixtures.js`'s grant plan and `seeds/01_dev_tenants.js`'s `ensureManagerReservationsAccess` backfill (verified live against the real dev database: both seeded managers now hold all four keys).

**Real bugs and gotchas hit while building, not by inspection** (same discipline as every earlier pass): (1) the concurrency-test harness limitation above — not a bug in the product, but a real trap: a first draft of RES-5 using `Promise.all` against the shared-transaction harness passed with **both** requests succeeding, silently proving nothing. (2) The table-level `.comment()`-doesn't-escape-apostrophes bug from Phase 1 recurred verbatim in the `reservations` migration's own comment string — caught immediately by the same class of migration-apply failure, fixed by rewording rather than escaping. (3) MySQL's 64-character identifier limit was hit again, this time on `reservation_daily_rates`'s FK and index names — shortened the same way Phase 1's `rate_calendar` migration already had to. (4) `guests` needed its own `UNIQUE(tenant_id, id)` parent-key index added explicitly before `guest_accounts.guest_id`'s FK could reference it — InnoDB needs the referenced columns to be a leftmost index prefix on the parent, and a bare TENANT_SCOPED table doesn't get one for free the way `properties`/`rooms`/`room_types` already did from earlier migrations.

**Frontend**: one self-contained `BookingScreen` (`src/app/booking/`) with five tabs (Availability, Tape Chart, Reservations, Waitlist, Front Desk) — the same multi-tab pattern `SetupScreen` established, mounted under the literal `nav-config.js` "Booking" label from PRODUCT_REQUIREMENTS.md's App-shell spec (confirmed as the Reservations module by that same spec's own Manager-dashboard KPI line, "Total Booking → Reservations") rather than inventing a differently-named nav item; Front Desk has no separate top-level slot in the literal spec either, so it lives as this screen's fifth tab. `nav-config.js`'s `booking` item is gated on `reservations.view` — the second real (non-Setup) permission-gated nav item this codebase has had.

**The tape chart is real, per this session's confirmed scope (grid-with-bars, no drag-to-move — room moves go through Front Desk's dedicated form instead), but plots room TYPE rows, not physical-room rows — a genuine, flagged adaptation, not a shortcut.** A traditional tape chart needs a room pre-assigned at booking time to have something to draw a bar against; this pass's own confirmed decision (above) is the opposite — a room is assigned only at check-in — so a future confirmed reservation has no physical room to plot yet. `TapeChartTab` instead shows each room type's sellable position per date across a 14-day window (reusing the same `checkAvailability` the Availability tab calls), which answers the same underlying question a tape chart exists for — booking pressure across dates — honestly, given what this pass's data model actually supports before check-in.

**Two more flagged, deliberate simplifications**: (1) FD-5/FD-6's early/late checkout fee logic (`computeEarlyLateFee`, pure and directly unit-tested) has no property-level "scheduled departure time" configuration to read from — PRODUCT_REQUIREMENTS.md §3.3 names such a setting, Phase 1 never built it — so the check-out endpoint and `FrontDeskTab`'s check-out form both accept the scheduled/actual times and fee amounts as explicit, optional inputs each time rather than pretending a config source exists. (2) Front desk's Arrivals/Departures boards filter against `properties.current_business_date` (ARCHITECTURE.md §6, never wall-clock) — real code, but nothing in this codebase advances that date yet beyond its value at property creation, since business-date rollover is Night Audit (§3.10) territory, not built.

## Status: Phase 1 — Property setup, partially built (not PLAN.md's full exit criterion)

**Scope, stated plainly**: PLAN.md's Phase 1 bullet list is longer than what this pass built. Built: property record creation (name/timezone/currency/opening business date), room types, physical room inventory with bulk range-entry, rate codes and a rate calendar, and effective-dated tax configuration — the five items explicitly requested, each confirmed against this session's own clarifying questions. **Not built, deliberately**: user-management UI (Phase 0's tables already support it — this is a UI gap, not a schema one), market segments, booking sources, cancellation policies, and the guided setup wizard with resumable progress. PLAN.md's own Phase 1 exit line — "a fresh tenant can configure a complete property unaided" — is therefore **not yet true**; don't read this section as claiming it.

**A new backend pattern this phase introduces**: every earlier cross-table reference in this schema was `PROPERTY_SCOPED` child → `TENANT_SCOPED` parent (e.g. `user_property_access.role` → `roles.code`), needing only a 2-column `(tenant_id, id)` parent key. This phase is the first time one `PROPERTY_SCOPED` table references *another* `PROPERTY_SCOPED` table (`rooms.room_type_id` → `room_types`, `rate_calendar.rate_code_id`/`room_type_id` → `rate_codes`/`room_types`) — that needs a **3-column** parent key, `(tenant_id, property_id, id)`, or a room could reference a room type belonging to a different property in the same tenant. `room_types` and `rate_codes` each carry that composite unique key for exactly this reason (see each migration's own header).

**The RBAC catalogue's first real entries**: `rbac.js`'s own header always said the literal permission catalogue "arrives one key at a time as each real module lands" — Phase 1's setup module is that first real module. `20260905095000_seed_setup_permissions.js` migration-seeds `setup.view`/`setup.manage` for real (not fixture-only); `tests/helpers/fixtures.js`'s permission-seeding loop was changed from a blind insert to select-or-insert so it composes with a real migration-seeded catalogue instead of colliding with it — a real conflict this pass hit and fixed (`tests/audit/audit.test.js` had its own redundant ad-hoc grant removed once `fixtures.js` started providing it directly). Manager gets `setup.view` only (read-only); Admin/Super-admin get both — this session's confirmed decision, now real in both the migration and `tests/helpers/fixtures.js`'s grant plan, and backfilled into the dev seed script (`seeds/01_dev_tenants.js`) so the dev-seeded manager account can exercise the Setup screens live.

**A genuine, flagged architectural gap**: property *creation* cannot be gated by `requirePermission` the normal way — creating a tenant's very first property happens before any `user_property_access` grant exists to check a role against, and `requirePermission` always checks "at the active property." `POST/PATCH/GET /properties` are gated by `authenticate('staff')` only, no permission check — safe today only because Phase 0 has no self-service signup (every `users` row comes from the dev seed script or a fixture, not a stranger). Real tenant/first-admin provisioning is Phase 5 (SaaS platform) territory and isn't solved here; flagged rather than papered over with an invented rule.

**Two real bugs found by writing tests against the real HTTP layer, not by inspection** (same discipline as every earlier pass this session): (1) no generic mapping from a MySQL duplicate-key error to `AppError` existed anywhere in this codebase — an unwrapped `ER_DUP_ENTRY` fell through to a bare `500 INTERNAL_ERROR` instead of API.md §3's `409 CONFLICT_`. Fixed with `DuplicateEntryError`, wrapped around every create in `src/modules/setup/service.js` that can hit a UNIQUE constraint. (2) Every by-`:id` update/archive controller handler fetched a `before` row but never checked it — a cross-tenant id silently updated zero rows and returned a broken `200` with no `data` key at all, instead of 404. Caught while writing the isolation test for exactly this case; fixed by adding `if (!before) return notFound(res);` to all six affected handlers. A third, frontend-side version of the same class of bug: `SetupScreen`'s property-load failure path set an error message but never left its `properties === null` loading gate, so a failed initial fetch showed "Loading setup…" forever with the error banner unreachable — fixed to set `properties: []` on failure too.

**Tax effective-dating, tested without Phase 2's folio schema**: PLAN.md's Phase 1 gate wants proof that "a tax rate change does not alter an existing folio's tax," but folios are Phase 2. This session's confirmed resolution: `resolveEffectiveTax(versions, businessDate)` in `src/modules/setup/service.js` is a pure function (no database, no folio) proving the actual rule — a date resolves to whichever version was effective *on that date*, regardless of what's changed since — directly unit-tested (`tests/setup/pure-functions.test.js`) and exercised end-to-end through the real `POST /taxes`/`GET /taxes/resolve` endpoints (`tests/setup/setup.test.js`). "Changing a tax rate" is always a new row with its own `effective_from`; the version it supersedes gets `effective_to` closed out in the same transaction, never its `rate` touched.

**Frontend**: one self-contained `SetupScreen` (`src/app/setup/`) with five tabs (Property, Room Types, Rooms, Rate Codes & Calendar, Taxes) — the same multi-view pattern `StaffLoginScreen` already established, since this app still has no router. `nav-config.js` gets its first `requiredPermission`-gated real item (`setup`, gated on `setup.view`) — every earlier nav item had none, deliberately, because no real permission existed to gate by; this is that first real one. **A related, flagged gap**: `main.jsx` passes `permissions={new Set(['setup.view', 'setup.manage'])}` unconditionally, because no endpoint returns what a signed-in user can actually do (a `GET /api/v1/me/permissions`-shaped read, not built). The Setup nav item is therefore visible to every role, not correctly filtered — but per CLAUDE.md's own line, "UI-level RBAC ... is convenience only — the API check ... is the real one," and that real check is verified working end-to-end (both in `tests/setup/setup.test.js` and live against the dev database): a role with no `setup.manage` grant gets a genuine 403 from the backend, not a security hole, just an undiscriminating nav item pending a real permissions-read endpoint. The rate calendar is a single-date resolve-and-override panel, not a visual month grid — `DataTable` has no 2D-matrix support and a real calendar-grid component was out of scope for this pass; the underlying resolution rule (TESTING.md SET-6) is fully real and tested, only the visual grid is deferred. CSV room import is deliberately not built — PRODUCT_REQUIREMENTS.md's bulk-add requirement is satisfied by the real range-based `POST /rooms/bulk` endpoint and UI; CSV import overlaps with the separate, fully-specified Data Migration module (§3.20, itself Phase 5), and a parallel one-off parser would duplicate that work rather than reuse it.

## The scoped accessor is the only query path

Every module reaches the database through `src/modules/tenancy`, never through `knex` directly:

```js
const db = scopedDb.for(contextFromSession(req.session));
await db.table('reservations').where({ status: 'confirmed' });   // tenant_id + property_id injected
await db.acrossProperties().table('user_property_access').where({ user_id });  // tenant_id only
```

`table()` reads the entity's scope from `src/shared/table-scopes.js` and injects the predicates that scope requires; a table with no declaration there has no query path at all. The returned object is **not** a knex builder — it deliberately does not expose a top-level `orWhere`, because knex applies one at the same level as the scope predicate, so `.where({tenant_id: 1}).orWhere({id: 5})` reads every tenant's rows while looking scoped at the call site. Disjunctions go through a callback that is wrapped in its own parenthesised group. Before execution the compiled SQL is re-checked for the scope predicate and its binding.

`acrossProperties()` drops `property_id` and never `tenant_id` — it exists for the two queries that legitimately precede an active property (login's "which properties may this user work at") or deliberately span them (the multi-property module). A new tenant-owned table inherits the whole `ISO-*` suite by adding one entry to `tests/helpers/entities.js`.

`npm run lint` enforces the import half of this: `knex` and `mysql2` may only be required from `src/db`, `src/modules/tenancy`, and the test helpers. The accessor cannot stop a module importing knex directly — nothing at runtime can — so that rule is the control, not code review.

## Architecture invariants

These are the rules most likely to be violated by code that otherwise looks correct. Each has a fuller treatment in the file cited.

**Tenant isolation is architectural, not disciplinary** (`SECURITY.md` §2, `ARCHITECTURE.md` §3). Every table declares one of four scopes — PLATFORM_SCOPED, TENANT_SCOPED (`tenant_id` only), PROPERTY_SCOPED (`tenant_id` + `property_id`), GLOBAL_REFERENCE — and is reached only through the scoped accessor that injects the right `WHERE` clause. There is no unscoped query path; raw table access in a module is a review-blocking defect. `tenant_id` comes from the session, never from a request body, query param, or header. Cross-tenant record access returns **404, never 403** — a 403 confirms the record exists.

**A user's role is per property, not global** (`SECURITY.md` §3–4). Roles live in `user_property_access`; `manager` at property A and `front_desk` at property B is normal. `if (user.role === 'manager')` is wrong by construction — the check is always "does this user hold this role *at this property*". The token carries `tenant_id`, role, and user id, never a single hardcoded `property_id`; active property is session state changed only via `POST /api/v1/auth/switch-property`, re-verified server-side.

**Three identity populations, three route trees** (`API.md` §4). `/api/v1/*` accepts staff tokens only; `/api/v1/portal/*` guest tokens; `/api/v1/platform/*` platform-staff tokens with an active, audited impersonation grant. A wrong-audience token gets `401 AUTH_WRONG_AUDIENCE`. Public routes are public because they are on the explicit allow-list, never because a decorator was forgotten.

**Money is exact, always** (`ARCHITECTURE.md` §1 data conventions, §12). `DECIMAL` in MySQL, DECIMAL-as-string in JSON (`"1250.00"`), a fixed-precision decimal library in application code. Never float, anywhere, including FX conversion. Every money column carries its currency. Test assertions are exact string comparisons — never `toBeCloseTo`.

**Financial records are immutable** (`ARCHITECTURE.md` §8). A correction is an offsetting row plus a new correct row, never an `UPDATE` to a posted charge's amount. The only mutable fields on a financial row are the audited void fields (`voided_at`, `void_reason`, `voided_by_user_id`). Void, never delete; FKs on financial tables use `RESTRICT`, not `CASCADE`.

**Idempotency covers every financial mutation** (`ARCHITECTURE.md` §7), not just gateway payments — refunds, voids, POS room-charge postings, checkout, and reservation state transitions all take an `Idempotency-Key` header. The first call's response is *stored* and replayed verbatim within the retention window (~24h, keyed on tenant + operation type + key value). The same key with different material parameters is rejected as `409 CONFLICT_IDEMPOTENCY_KEY_REUSE`, never silently processed or silently replayed.

**A database transaction cannot commit atomically with a payment provider** (`ARCHITECTURE.md` §7). The flow is always: local intent row → external call → verify/dedupe the webhook → apply the state transition and the folio line item in one local transaction. Payment status follows the fixed state machine (`INITIATED → PENDING → AUTHORIZED → CAPTURED`, plus the terminal branches); modules never invent ad hoc status strings. Webhooks are verified by signature, persisted before processing, deduplicated on the provider's event id, and answered `200` on persistence rather than after processing.

**Concurrency uses database locks, not check-then-write** (`ARCHITECTURE.md` §5). The named races — last room, double settlement, POS tab edit, room assignment, duplicate night audit, stock depletion, payment reconciliation — each have a required mechanism (row lock, atomic decrement with an affected-row check, unique constraint, or idempotency key). Reading availability and then writing a reservation in separate unlocked steps is the specific anti-pattern to avoid, and "add another check" never fixes it.

**Business date ≠ wall clock** (`ARCHITECTURE.md` §6). Every posted transaction stores `business_date` separately from `created_at`; the property's business date is the accounting truth, and each property is at a different point in time. Night audit is a 13-step sequence where steps 4–13 are one transaction, guarded by a `night_audit_runs` row with its own state machine (`READY → RUNNING → COMPLETED`, plus `FAILED`/`STALE`/`RECOVERABLE`) and heartbeat. Recovery after a crash checks reality (does a `daily_reports` row and an advanced business date already exist?) rather than trusting the run row. Retry is a fresh run from step 1, never a partial resume.

**Side effects leave the database through the outbox** (`ARCHITECTURE.md` §13). Emails, notifications, exports, reports, and external webhook calls are written as outbox event rows inside the business transaction and dispatched afterwards by a separate BullMQ worker draining `outbox_events`. An external HTTP call inside a financial transaction is a defect. Anything long-running belongs in `/jobs`, never an inline request handler.

**Redis is infrastructure, never a source of truth** (`ARCHITECTURE.md` §14). MySQL holds everything durable; Redis holds the BullMQ queues, rate-limit counters, and short-lived cache. Losing it pauses jobs and resets limits, and must never put financial data at risk. One queue per job category — `night-audit`, `outbox-dispatch`, `reports`, `imports`, `exports`, and `email` (separate from `outbox-dispatch` so an email-provider outage can't back up report generation) — not one global queue. Every payload carries `tenant_id`, and each worker enforces a per-tenant concurrency cap; that cap is what "one large customer can't starve the rest" actually means in practice. **Jobs must be idempotent**, because BullMQ retries: a retried `night-audit` job has to hit the same §6.2 guard a manual re-trigger does. A job never writes financial data outside a transaction it owns — the critical transaction has already committed by the time it runs, and the job's work is the side effect, not the money. Jobs that exhaust their retry policy land in a dead-letter state visible to platform staff; one that silently disappears is the async equivalent of a swallowed exception.

**Rate limiting is Redis-backed, never in-memory** (`ARCHITECTURE.md` §15). `express-rate-limit` with `rate-limit-redis` — in-memory counters reset on every deploy and stop working entirely once more than one backend instance runs behind a load balancer. Three tiers, deliberately different shapes: **auth** is per-account *and* per-IP (per-IP alone locks out a whole shared front-desk terminal when one person mistypes their password — both dimensions are required, not either); **general API** is per-tenant and generous, guarding against a runaway client rather than malice; **public/guest** is per-IP and per-token, the only surface where a hostile actor has no account to lock. Responses are `429 RATE_LIMITED` with a `Retry-After` header (`API.md` §3). Webhooks are exempt from the per-tenant limit but carry their own ceiling.

**Tax and FX are historically reproducible** (`ARCHITECTURE.md` §12). Taxes are effective-dated and always calculated against the version effective on the charge's `business_date`, so a folio audited six months later reproduces the same numbers. `inclusive`/`compound`/`priority`/`rounding_method` are explicit per tax, never assumed. FX rates lock at commitment (booking confirmation or capture) and are stored against the transaction; residual FX differences post as their own labelled adjustment line.

**IDs** (`ARCHITECTURE.md` §10): `BIGINT UNSIGNED` PKs, serialized as **strings** in JSON (JS loses precision above 2^53). UUID/ULID only for values that must be safe to expose — confirmation numbers, QR tokens, reset tokens. Idempotency keys are never resource IDs.

**Configuration, never code branches** (`PRODUCT_REQUIREMENTS.md` §1.1). Branding, tax rules, rate structures, currency, room types, templates, enabled features, gateway choice, and lock-vendor adapter are all config rows. An `if (tenant === '...')` is a design failure. Feature gating goes through the single entitlement check and is enforced at the API, not just hidden in the UI.

**Migrations run against every tenant at once** (`DATABASE.md`). Backwards-compatible and reversible; never drop a column in the same release that stops writing to it. A new table adds its uniqueness constraint in the same migration that creates it (`DATABASE.md` §2 lists the required set) and declares its scope before it can be queried.

## Module boundaries

`/backend/src/modules/<module>` is self-contained — routes, controller, service, model. Cross-module calls go through service functions, never direct model access. `/frontend/src/features` mirrors the backend module names so a change traces across both sides. All network calls go through `/frontend/src/shared/api` (the single place tenant context, auth headers, and error handling are applied); all design tokens live in `/frontend/src/styles/tokens.css` and nowhere else. The guest portal ships from the same frontend app under `/portal` — shared booking/availability/payment logic, separate route tree so admin styling cannot leak into a guest-facing page.

## API contract essentials

Base path `/api/v1`; every response is `{ data, meta, error }`, success or failure. Error codes are namespaced by domain (`VALIDATION_`, `AUTH_`, `FORBIDDEN_`, `CONFLICT_`, `PAYMENT_`, `BUSINESS_RULE_`, `LOCKED_`, `INTERNAL_`) with a stable machine-readable `code`, a human sentence for `message`, and a `request_id` that matches the audit log row for that request. Tenant/property scope is implicit from the session and never a URL segment or body field. Non-CRUD actions are `POST /resource/{id}/action` (check-in, void, cancel, refund), not an overloaded `PATCH` with a status field — this keeps the audit `action` column one-to-one with endpoints. Filter and sort parameters come from an explicit per-endpoint allow-list.

## Frontend

Every screen ships all six states — loading (skeletons at real dimensions, never a spinner over stale numbers), empty, success, error, confirm, offline — alongside the happy path, not afterwards (`DESIGN_SYSTEM.md` §2). Money confirmations require a reason field that feeds the audit trail. Offline handling must disable financial actions rather than silently queueing a payment as though it succeeded. No literal hex, spacing, radius, font size, or currency symbol in a component file — everything comes from tokens, or tenant theming silently breaks. Status is always a filled pill with a text label, using the system-wide status colour vocabulary; money columns use tabular figures. UI-level RBAC (filtered sidebar, role landing pages) is convenience only — the API check against `SECURITY.md` §5's matrix is the real one.

## Definition of done

`TESTING.md` Part 1 carries the full checklist and Part 2 enumerates all 134 test cases by ID. A module is unfinished — not "shipped, tests pending" — until its required tests pass. Specifically: every new tenant-owned entity gets a cross-tenant isolation test (the table-driven `ISO-*` suite, so a new endpoint inherits coverage automatically) before it ships; a failing test or a stray `.only`/`.skip` blocks the merge; every production bug gets a failing test reproducing it *before* the fix. Coverage is by risk, not a blanket percentage — money, night audit, availability, isolation, and auth need every branch including failure paths.
